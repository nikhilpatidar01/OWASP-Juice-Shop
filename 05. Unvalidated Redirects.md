# Unvalidated Redirects Total 2 hacking Challenges

* When a website lets users **redirect to any link** without checking if it’s safe.
* Attackers trick users into opening **malicious sites**.

### How Attackers Exploit
* Phishing emails with legit-looking links (site.com/redirect?url=evil.com).
* Malicious redirects → Fake login pages.
* Malware hosting → Directing victims to download harmful files.

### **Example**

✅ Legit:

```
http://example.com/redirect?url=http://example.com/home
```

❌ Exploit:

```
http://example.com/redirect?url=http://evil.com
```
> User thinks they’re going to `example.com` but lands on `evil.com`.

### **Fix**

* Allow only **safe (whitelisted) URLs**.
* Use **relative paths** (`/home`, `/dashboard`) instead of full links.

# 1. Outdated Allowlist

**Definition:**
An Outdated Allowlist occurs when an application uses an old list of trusted inputs (such as domains, URLs, or addresses) that is not updated. Attackers can exploit these outdated entries to bypass validation or redirect users to unsafe destinations.

**Vulnerable Parameter:**
* Navigate to **Dashboard**
* Open **Inspect (Ctrl+Shift+I)** → **Sources** → **main.js**
* Search for **redirect**
* Locate the **URL redirect function**
* Set a **breakpoint** and Allow *Pause on uncaught exceptions*

**Exploit:**
Use one of the outdated cryptocurrency donation addresses still present in the application.

**Payload:**
```
http://10.30.30.145:3000/redirect?to=https://blockchain.info/address/1AbKfgvw9psQ41NbLi8kufDQTezwG8DRZm
```
**Result:**
> The application redirects to a deprecated crypto address, completing the challenge.

**Fix:**
* Regularly update allowlists.
* Remove deprecated or unused entries.
* Validate destinations strictly (exact domain/format checks).
